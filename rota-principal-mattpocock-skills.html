Documentação de referência · v4

Rota Principal: da ideia ao ship

Documentação das skills do mattpocock/skills, estação por estação. Cada card abre uma anotação técnica com mais contexto, para nenhuma dúvida ficar para trás.

Os comandos valem tanto para o terminal quanto para o plugin do Claude Code no VS Code. Onde o comportamento muda de um para o outro, isso está anotado no contexto da estação. A legenda e o índice ficam sempre visíveis na barra ao lado.

Significado das siglas usadas aqui
ADRArchitecture Decision Record. Um registro curto de uma decisão de arquitetura difícil de reverter, o porquê dela, e o que foi descartado no caminho.
PRDProduct Requirements Document. O documento de requisitos que descreve o que precisa ser construído. Hoje o pacote chama esse documento de spec, mas PRD é o nome mais conhecido de mercado.
TDDTest-Driven Development. Desenvolver escrevendo primeiro um teste que falha, depois o código mínimo para ele passar, e só então melhorando esse código.
CLICommand Line Interface. Interface de linha de comando, o terminal, em contraste com o plugin gráfico do VS Code.
IDEIntegrated Development Environment. O editor de código com ferramentas integradas, como o VS Code.
URLUniform Resource Locator. O endereço que aponta para uma página ou recurso na web, como o link de uma issue.

Pré requisito

Mesmo chat

Instalação e /setup-matt-pocock-skills

Instale o pacote de skills no seu projeto e rode o setup uma única vez por repositório. Ele pergunta qual rastreador de issues você vai usar, quais labels aplicar na triagem, e onde salvar a documentação de domínio.

Opção A · copiar

npx skills@latest add mattpocock/skills — arquivos editáveis dentro do seu repo.

Opção B · plugin

/plugin marketplace add mattpocock/skills — bundle somente leitura, sempre atualizado.

Mais contexto

Depois de escolher a opção A ou B, rode /setup-matt-pocock-skills dentro do seu agente. Sem esse passo, as outras skills não sabem onde gravar a documentação nem qual rastreador de issues consultar, e algumas vão parar para perguntar isso no meio do fluxo.

Se você não tem certeza de qual rastreador escolher, arquivos locais é a opção mais simples para um primeiro teste, sem depender de conta em GitHub ou GitLab. Existem quatro opções na real, GitHub e GitLab como integrações de verdade, usando a CLI oficial de cada um, local em markdown, e uma quarta opção "outro", que cobre Linear, Jira e qualquer outro rastreador. Nessa quarta opção você só descreve seu fluxo de trabalho num parágrafo, e o setup grava isso como texto livre, sem integração automática de verdade. Ou seja, Linear funciona, mas não do mesmo jeito nativo que GitHub ou GitLab, é mais uma anotação de como você trabalha do que uma conexão de fato.

Funciona também num projeto que já existe no GitHub e nunca usou nenhuma dessas skills antes. O que importa é ter um repositório, não ter usado a skill antes. Instale o pacote nesse projeto, rode o setup, e o /grill-with-docs já vai explorar o código existente para responder perguntas e começar o CONTEXT.md e os s do zero, mesmo que o projeto já tenha bastante código escrito sem essas skills.

Documentação de domínio para monorepo: o setup assume por padrão um único CONTEXT.md na raiz do projeto. Se ele detectar sinais de monorepo, várias partes bem separadas dentro do mesmo repositório, oferece em vez disso uma estrutura de múltiplos contextos, mais de um CONTEXT.md, um por área. Isso só aparece se o setup identificar esse cenário, não é algo que você escolhe do nada.

Manter atualizado sem o plugin: se você instalou copiando os arquivos para dentro do repositório, em vez do plugin, use npx skills update de vez em quando para puxar as versões mais novas das skills. Quem instalou como plugin não precisa disso, o bundle já se atualiza sozinho.

Estação 1 de 4

Mesmo chat

/grill-with-docs

Descreva a funcionalidade ou mudança que você quer construir. O agente te entrevista de forma insistente até esgotar as ramificações da decisão, e vai escrevendo em CONTEXT.md e em s os termos e decisões que surgirem.

Mais contexto

Essa entrevista existe para fechar a lacuna de comunicação entre você e o agente antes que qualquer código seja escrito. É o ponto mais barato para corrigir um mal entendido.

Repita essa estação quantas vezes fizer sentido. Uma segunda rodada, já com CONTEXT.md mais maduro, costuma levantar perguntas mais finas.

Significados
ADRArchitecture Decision Record. Um registro curto de uma decisão de arquitetura difícil de reverter, o porquê dela, e o que foi descartado no caminho.

Comandos úteis · não obrigatórios

/grill-me

Qualquer sessão

A mesma entrevista relentless do /grill-with-docs, mas para quando você ainda não tem repositório nenhum, só uma ideia que quer amassar antes de criar o projeto.

Mais contexto

O critério que decide entre os dois não é se o plano é vago ou concreto, é se existe um repositório. Com repositório, mesmo que inicial ou quase vazio, use /grill-with-docs: ele lê o código para responder perguntas e grava o aprendizado em CONTEXT.md e s. Sem repositório nenhum ainda, use /grill-me: mesma entrevista, mas não grava nada em disco, o único resultado é o entendimento na própria conversa. Por ser stateless, funciona em qualquer sessão, sem depender de nada aberto antes.

Comandos úteis · não obrigatórios

/handoff

Depende

Condição: só use quando for realmente sair da conversa atual para uma sessão nova, preservando o que já foi decidido.

Não é nativo do Claude Code, é uma skill do pacote, acionada só por você. Compacta a conversa atual num arquivo markdown para uma sessão nova continuar de onde parou.

Mais contexto

Ao rodar, ela escreve o arquivo na pasta temporária do sistema operacional, não na pasta do projeto, resumindo a conversa e sugerindo quais skills a próxima sessão deveria usar.

No plugin do VS Code, o caminho é: rodar /handoff na conversa atual, ele devolve o caminho do arquivo gerado, você abre uma aba nova de conversa dentro do próprio plugin e referencia esse arquivo nela. Ao terminar, roda /handoff de novo nessa aba nova para trazer o caminho de volta.

Esse vaivém não é exclusivo do /prototype. Funciona do mesmo jeito a partir de uma conversa de /grill-me, ou de qualquer outra sessão que você queira bifurcar preservando contexto.

/compact

Mesmo chat

Recurso nativo do Claude Code, não é uma skill do pacote. Resume os turnos anteriores da própria conversa, sem abrir nada novo.

Mais contexto

Use em pausas intencionais entre fases, quando não se importa em perder o histórico literal. Evite compactar no meio de uma fase, como no meio de uma entrevista de /grill-with-docs ainda em andamento, o agente pode perder o rumo.

/handoff bifurca para outra sessão. /compact continua na mesma.

/prototype

Depende

Condição: mesmo chat se rodado na conversa que já está discutindo o design. Chat novo se veio pelo caminho de /handoff da estação 02.

Constrói um protótipo descartável para responder uma dúvida de design, um app de terminal rodável para dúvidas de estado e lógica, ou várias variações de tela radicalmente diferentes, alternáveis a partir de uma única rota.

Mais contexto

Dá para discutir a tela em si dentro do próprio /grill-with-docs, decidindo estrutura, fluxo, o que aquela parte da interface precisa fazer. Quando a dúvida só se resolve vendo de verdade, aí entra o /prototype, gerando as variações para você comparar lado a lado antes de decidir.

Enquanto o /prototype escreve esse código de tela, o Claude também aplica sozinho a skill de frontend design descrita no card ao lado, então cada variação já nasce com uma direção visual cuidada, não só estruturalmente diferente uma da outra. É por isso que os dois valem a pena juntos, o /prototype decide o quê comparar, o frontend design cuida de como cada opção fica pronta na tela.

Não é um comando de skill

Frontend design do Claude

Qualquer sessão

Não vem do pacote do mattpocock e não se digita como comando. É uma skill do próprio ambiente do Claude, consultada sozinha sempre que ele vai escrever código de interface, React, Vue, HTML, um componente novo.

Mais contexto

Funciona como uma camada a mais de pensamento antes de gerar a tela, sobre direção estética, tipografia, e como evitar que a interface saia com cara de padrão genérico. Não decide o quê construir, isso é papel do grill e do /prototype, decide como aquilo vai ficar visualmente uma vez construído.

Não precisa fazer nada para ativar, ela entra sozinha no momento de escrever a interface, dentro ou fora de uma sessão de /prototype.

03

Bifurcação · você decide

Depende

Condição: /to-spec e /to-tickets ficam sempre no mesmo chat. Chat novo só entra depois, um por ticket, ao rodar /implement.

O trabalho cabe em uma sessão, ou é um build grande?

Trabalho grande, que vai se espalhar por várias sessões de implementação, ganha um documento de requisitos e uma quebra em tarefas menores antes de codar. Trabalho pequeno vai direto para a implementação.

Build grande · mesmo chat

/to-spec organiza tudo que já foi discutido na entrevista, mais o que o agente entende do código, num documento formal de requisitos. Ele não te entrevista de novo. Depois /to-tickets corta esse documento em pedaços pequenos e independentes, prontos para implementar um de cada vez.

Cabe numa sessão · mesmo chat

Pule direto para /implement, também na mesma janela de contexto em que você grillou. Sem spec nem tickets, porque a própria conversa já tem tudo que a implementação precisa.

Mais contexto

Nota de nomenclatura: essas duas skills já se chamaram /to-prd e /to-issues em versões anteriores do repositório. Hoje os nomes são /to-spec e /to-tickets, esta última fundida com uma antiga /to-plan. O comportamento é o mesmo, só o nome do comando mudou.

Onde a spec () fica salva: no rastreador que você escolheu no /setup-matt-pocock-skills. Se foi arquivos locais, vira um arquivo markdown de verdade dentro de uma pasta .scratch/<funcionalidade>/ no seu repositório. Se foi GitHub ou GitLab, vira uma issue real lá. Em qualquer caso, você consegue abrir e editar antes de seguir, e vale a pena revisar aqui, é o ponto mais barato para corrigir algo antes de quebrar em tickets.

Como os tickets nascem: cada um é uma fatia que atravessa todas as camadas do sistema de ponta a ponta, banco, API, tela, teste, em vez de ser uma camada inteira sozinha. Se local, viram arquivos dentro de .scratch/<funcionalidade>/issues/, cada um dizendo o que bloqueia o quê, trabalhados na mão seguindo essa ordem. Se GitHub ou GitLab, viram issues de verdade com links nativos de bloqueio entre elas, e qualquer ticket cujos bloqueios já foram resolvidos pode ser pego. Você vai ticket por ticket, implementando, revisando e só então passando para o próximo liberado. O motivo de fazer isso é poder revisar e testar em pedaços pequenos, em vez de uma implementação gigante de uma vez só.

Como apontar o /implement para um ticket específico: você referencia ele direto na sua mensagem ao chamar o comando. Para um ticket no GitHub ou GitLab, escreva algo como /implement issue #14 ou cole a da issue. Para um ticket local, escreva /implement seguido do caminho do arquivo, por exemplo /implement .scratch/carrinho/issues/03-validar-cupom.md.

O critério não é se o projeto é novo, é se o trabalho cabe numa sessão de implementação ou vai se espalhar por várias. Dentro da bifurcação em si, não existe chat novo, ele só entra depois, uma vez para cada ticket.

A issue publicada pelo /to-spec é uma issue normal do GitHub, sem nada de protegido. Você pode editar o corpo dela ou comentar à vontade. Editar o corpo muda diretamente o que as próximas skills vão ler como fonte da verdade. Comentar não desaparece, mas não é lido sozinho, então aponte o comentário explicitamente na próxima chamada se quiser que seja considerado.

/to-tickets não precisa que você referencie a spec se ainda estiver na mesma conversa onde ela foi publicada, ele lê automático o que já está no contexto. Só referencie pelo número ou pela URL, do mesmo jeito que no /implement, se abrir uma sessão nova sem esse histórico, ou se houver mais de uma spec discutida na mesma conversa e for preciso deixar explícito qual delas quebrar.

Estação 2 de 4

Depende

Condição: mesmo chat se o trabalho coube numa sessão só, na estação 03. Chat novo, um por ticket, se veio da rota de build grande.

/implement

É aqui que o código de fato é escrito. Você aponta a spec ou o ticket, e o agente constrói o que foi combinado, escrevendo o código de verdade.

Enquanto implementa, ele não escreve tudo de uma vez e espera dar certo. Ele segue um passo a passo chamado /tdd (, Test-Driven Development): primeiro escreve um teste que descreve o comportamento esperado e que ainda falha, porque o código não existe. Depois escreve o código mínimo para esse teste passar. Só então melhora e organiza esse código, rodando o teste de novo a cada mudança para garantir que continua passando. Esse ciclo se repete pedaço por pedaço, até o trabalho estar pronto.

Mais contexto

A vantagem prática desse passo a passo é que o agente nunca fica "no escuro" sobre se o que ele escreveu funciona. Cada pedaço de código tem um teste que prova, na hora, se ele está certo ou errado, em vez de você só descobrir problemas depois, olhando o resultado final pronto.

Significados
TDDTest-Driven Development. Desenvolver escrevendo primeiro um teste que falha, depois o código mínimo para ele passar, e só então melhorando esse código.

Comandos úteis · não obrigatórios

/diagnosing-bugs

Depende

Condição: mesmo chat se o bug aparecer durante o /implement atual. Chat novo só se for um bug antigo que você está retomando depois, fora de uma implementação em andamento.

Disciplina de investigação para quando algo já quebrou e o motivo não é óbvio. Não é preventiva, só entra em ação depois que o erro apareceu.

Mais contexto

Você aciona dizendo algo como "diagnostica isso" ou "debuga isso", relatando um bug, dizendo que algo está quebrado, lançando erro, ou falhando. Para um erro simples e óbvio, o agente corrige direto, sem precisar dessa disciplina inteira.

O processo é investigativo: reproduzir o problema, isolar a menor parte do código que causa ele, levantar uma hipótese do porquê, adicionar instrumentação para confirmar essa hipótese, corrigir, e por fim testar que o problema não volta a acontecer.

/tdd

Mesmo chat

O motor de que o /implement já aciona sozinho nos pontos combinados, mas também pode ser chamado direto, fora de uma implementação inteira, para um pedaço isolado de código que você quer nascer já testado.

Mais contexto

O ciclo é sempre o mesmo: escrever um teste que descreve o comportamento esperado e que ainda falha, escrever o código mínimo para ele passar, e só então melhorar e organizar esse código, rodando o teste de novo a cada mudança.

Vale chamar sozinho quando você já está no meio de uma sessão de código e quer aplicar essa disciplina a uma função ou módulo específico, sem precisar que isso venha de um ticket inteiro passando pelo /implement.

Significados
TDDTest-Driven Development. Desenvolver escrevendo primeiro um teste que falha, depois o código mínimo para ele passar, e só então melhorando esse código.

Estação 3 de 4

Mesmo chat

/code-review

É uma revisão do código antes dele ser commitado, parecida com o que um colega faria ao revisar seu pull request. Você não precisa chamar isso manualmente a cada ticket, o /implement já roda essa revisão sozinho, ao final de cada um, dentro da mesma sessão.

A revisão olha para duas perguntas diferentes, cada uma respondida por um agente separado, para uma resposta não influenciar a outra:

Pergunta 1 · qualidade

O código escrito segue o estilo e as convenções já usadas no resto do repositório, e não tem problemas comuns de código malfeito, como duplicação ou funções fazendo coisa demais.

Pergunta 2 · fidelidade

O que foi construído realmente entrega o que a spec ou o ticket pediam, sem ter deixado nada de fora nem ter feito algo diferente do combinado.

Mais contexto

Separar essas duas perguntas em agentes diferentes evita um problema comum: um revisor que está checando se o código está bonito acaba, sem perceber, relevando um pedaço que não faz o que deveria, porque a atenção estava no estilo, não no requisito.

O /code-review não faz push nem abre pull request, ele só revisa antes do commit. Depois que o commit acontece, dar push da branch e abrir o PR é Git comum, fora do pacote de skills, seja pela CLI do GitHub, seja pedindo direto ao agente como uma instrução de Git normal.

Vale incluir algo como Closes #14 na mensagem do commit ou no corpo do PR, apontando para o número daquele ticket. Isso fecha a sub-issue automaticamente quando o PR for mergeado, e libera qualquer outro ticket que estava esperando aquele terminar.

Mesmo com a chamada automática por ticket, vale rodar /code-review manualmente de novo ao final de um lote maior de tickets, numa sessão nova, como uma checagem final antes de considerar aquele pedaço do trabalho pronto, já que uma sessão fresca tende a julgar com menos viés do que a mesma sessão que acabou de escrever o código. O cuidado aqui é apontar explicitamente o que revisar, como o intervalo de commits ou os números das issues, já que a sessão nova não tem essa memória sozinha. Segurar o push de vários tickets só para essa revisão em lote vai um pouco contra a filosofia de incrementos pequenos do pacote, então um meio-termo razoável é continuar dando push ticket por ticket e usar essa revisão em lote como uma checagem extra periódica, não como a única.

Fora da rota · manutenção

Chat novo (recomendado)

/improve-codebase-architecture

Não é trabalho de funcionalidade, é manutenção. Rode sempre que tiver um tempo livre, em uma sessão separada da que você acabou de usar para implementar. Ela aponta oportunidades de simplificação no código.

Mais contexto

Nem tudo aqui é automático. O escaneamento do código e a geração do relatório visual são automáticos, você só roda o comando e ele varre o projeto sozinho. Escolher qual candidato seguir é decisão sua, o relatório mostra várias oportunidades ao mesmo tempo, com uma força de recomendação cada, forte, vale explorar, ou especulativo. A partir da escolha, a entrada na entrevista volta a ser automática, a skill já cai sozinha numa sessão de /grilling, o mesmo motor por baixo do /grill-with-docs, sem você precisar digitar esse comando à parte.

Ao escolher uma das oportunidades apontadas, isso vira uma ideia nova, que reentra na rota principal pela estação 01, o /grill-with-docs.

Rodar numa sessão nova evita que o julgamento sobre o código carregue o viés das decisões que você acabou de negociar durante a entrevista. É a mesma lógica por trás dos subagentes paralelos do /code-review.

Pode ser um chat totalmente novo, sem precisar procurar a conversa original. O /grill-with-docs não depende do histórico daquela conversa específica para funcionar, ele lê o CONTEXT.md e os s direto do repositório, que já têm tudo que foi decidido antes gravado em arquivo. É justamente essa a vantagem de guardar o estado em disco em vez de só na memória da conversa.

Fora da rota · entrada externa

Mesmo chat

/triage

Não faz parte da rota principal, é a porta de entrada para bugs e pedidos que chegam de fora do seu planejamento, um usuário reportando algo, uma ideia solta que você mesmo anotou. Ela move cada item por uma pequena máquina de estados até virar algo pronto para o /implement pegar, ou até ser descartado de forma registrada.

needs-triage → needs-info

Ponto de entrada de tudo que ainda não foi analisado. Se faltar detalhe, vai para needs-info e espera resposta de quem reportou.

ready-for-agent

Já existe um resumo claro o bastante para um agente implementar sozinho, sem precisar de você no meio.

ready-for-human

Exige julgamento, acesso externo ou teste manual. Não pode ser delegada a um agente.

wontfix

Rejeitada, e fica registrada para não ser discutida de novo no futuro.

Mais contexto

Ao analisar um item, o agente lê o relato inteiro, procura no código se aquilo já existe implementado, checa se algo parecido já foi rejeitado antes, e, se for um bug, tenta reproduzir antes de qualquer outra coisa. Se o item estiver incompleto mas valer a pena, ele pode rodar um /grill-with-docs embutido para lapidar antes de marcar como pronto.

Vale até em projeto solo. Qualquer ideia ou bug que você mesmo for anotando ao longo do tempo também pode passar por aqui antes de virar trabalho de verdade, em vez de ficar bagunçado numa lista solta.

A diferença real para ir direto ao grill é essa validação prévia. O grill assume que a decisão de construir já foi tomada, só falta decidir como. O /triage ainda não sabe se aquilo é real, se já existe, ou se já foi descartado, e boa parte das vezes nem chega a grillar, terminando em wontfix, needs-info, ou ready-for-human antes disso.

Você não precisa registrar a issue antes de rodar o comando. Pode contar a ideia direto em linguagem natural para o /triage, e ele mesmo cria a issue se ela não existir, além de já processar o estado dela. Também pode simplesmente abrir a issue direto no GitHub, sem label nenhuma, sem envolver o agente, ela fica como "Unlabeled" esperando, e na próxima vez que você rodar /triage, ele descobre sozinho e processa a partir dali.

Itens marcados wontfix não só fecham, também ficam resumidos numa pasta .out-of-scope/ no repositório. Da próxima vez que uma ideia parecida aparecer, o próprio /triage confere ali antes de tratar como algo novo, evitando reabrir uma discussão já encerrada.

Onde fica a lista depende do rastreador escolhido no /setup-matt-pocock-skills. No GitHub, é a própria aba de Issues, filtrada pelas labels de estado, needs-triage, needs-info, ready-for-agent, ready-for-human, wontfix. Em arquivos locais, cada item vira um arquivo dentro de .scratch/, com uma linha Status: no topo indicando o estado.

O estado que a gente cobriu é só uma das duas dimensões. Todo item triado carrega também um papel de categoria, junto com o de estado, algo como bug, melhoria, ou pergunta. Os dois rótulos vivem lado a lado na mesma issue, não um no lugar do outro.

Pull requests também podem entrar no triage. Existe uma opção no /setup-matt-pocock-skills, desligada por padrão, que faz o /triage tratar PRs externos como se fossem issues, mesmos estados, mesma máquina, só com pequenos ajustes, por exemplo ready-for-agent numa PR significa que já existe um resumo anexado e um agente deve seguir naquele diff, em vez de implementar algo do zero.

Depende

Condição: só entra quando o trabalho é grande demais até para uma entrevista de /grill-with-docs só resolver numa sessão.

/wayfinder

Para quando o trabalho é grande demais para uma sessão de entrevista só resolver, ele não passa pela estação 01. Em vez disso, mapeia o esforço como uma série de tickets de decisão no próprio rastreador de issues, cada um guardando uma pergunta cuja resposta é uma decisão a tomar, não um pedaço de código para escrever.

Mais contexto

Você resolve esses tickets de decisão um de cada vez, até o caminho até o destino final ficar claro. É a mesma ideia de resolver a incerteza aos poucos que o /grill-with-docs resolve numa conversa só, só que espalhada por várias sessões, porque o escopo é grande demais para uma só.

Comandos úteis, sem estação fixa

Skills reaproveitáveis, não amarradas a nenhum passo específico da rota. Separadas por para que servem, não precisam ser chamadas em ordem nem em algum ponto obrigatório.

Para aprender a fundo, fora do projeto

Diferente de tudo mais nessa página, isso não roda na sessão nem na pasta do seu projeto. É dono da própria pasta, uma por tópico que você quer aprofundar, sem relação nenhuma com o repositório que você está construindo.

Vale muito para o seu objetivo de aprender fazendo

/teach

Chat novo

Condição: sempre numa pasta própria, separada da pasta do projeto, uma pasta por tópico. Tecnicamente roda na mesma sessão de outra coisa, mas não faz sentido misturar, veja o porquê nos tópicos abaixo.

Transforma o diretório onde você roda o comando num espaço de ensino permanente, focado num único tópico, ensinado ao longo de várias sessões através de lições curtas em HTML, cada uma autocontida. Não compartilha workflow com nenhuma outra skill do pacote, é dono da própria pasta e vive só ali.

Uma pasta cobre um tópico só, não o projeto inteiro. Dentro desse tópico único existem várias lições numeradas, e é entre elas que você avança quando roda o comando de novo. Um assunto diferente, mesmo dentro do mesmo projeto, é sempre uma pasta nova, com sua própria entrevista de missão do zero.

Como usar na prática: na primeira vez, se o arquivo MISSION.md daquela pasta ainda estiver vazio, o próprio /teach para tudo e pergunta por que você quer aprender aquilo, antes de ensinar qualquer coisa. Esse motivo fica gravado e guia todas as lições seguintes. Diferente de uma explicação normal, ele não ensina a partir do que o modelo já sabe de cabeça, esse conhecimento é tratado como não confiável, ele primeiro busca fontes externas de confiança, registra em RESOURCES.md, e cita essas fontes dentro de cada lição.

As lições em si, numeradas e completas, ficam em ./lessons/. O ./reference/ guarda só um resumo comprimido de cada uma, tipo um cheat sheet para consulta rápida depois, não a lição inteira. Existe ainda um ./learning-records/, no estilo , guardando o que você já aprendeu, usado para calcular o que ensinar a seguir sem repetir nem pular etapas. Um estilo visual compartilhado nasce logo cedo para as lições parecerem parte de um curso só, não páginas soltas.

Quando rodar de novo, e como revisitar

Não existe gatilho automático nem prazo, você roda de novo simplesmente quando quiser continuar aprendendo aquele tópico, sem esperar nada terminar antes, pode ser no dia seguinte, uma semana depois, ou duas vezes no mesmo dia. O comando sozinho olha o MISSION.md e o ./learning-records/ para calcular a próxima lição no nível certo, você não precisa referenciar número de lição nem recontar o que já viu.

Para revisitar algo específico, o caminho garantido é reabrir o arquivo daquela lição direto em ./lessons/, é um HTML salvo de verdade, sem precisar do comando. Pedir para o próprio /teach revisitar também deve funcionar, já que o desenho dele usa prática de recuperação e repetição espaçada como método, trazendo conceitos antigos de volta entrelaçados nas lições novas, mas isso não está documentado com uma resposta garantida de como ele reage a esse pedido específico.

Mesma sessão ou sessão separada?

A continuidade mora na pasta, não na conversa, então tecnicamente as três formas funcionam, o próprio autor confirmou isso quando perguntado: ficar na mesma sessão que já está rodando outros comandos, chamar /teach de novo numa sessão nova, ou abrir uma sessão nova na mesma pasta e pedir a próxima lição. Na prática, ele mesmo diz que cada lição costuma ser uma chamada separada, não várias de uma vez seguidas logo no início, e o hábito mais comum é abrir uma sessão nova dentro daquela pasta e escrever algo como /teach próxima lição sobre <tópico>.

Mesmo sendo tecnicamente possível rodar na mesma sessão do seu projeto, misturar as duas coisas tende a confundir mais do que ajudar. Não é para uma explicação pontual, se você só precisa esclarecer algo na hora, pergunte direto na conversa que já está aberta. Reserve o /teach para quando o aprendizado em si for o projeto, não um efeito colateral de estar codando.

Por que não usar /handoff para chegar aqui

Não faz sentido, e vale ser direto sobre isso. O /handoff e o /teach não compartilham formato de estado nenhum. O /handoff gera um resumo pensado para outra sessão de planejamento ou implementação continuar um trabalho em andamento, o /teach lê os próprios arquivos da pasta dele, MISSION.md, RESOURCES.md, lessons/, sem saber interpretar um arquivo de handoff.

Se surgir uma dúvida de aprendizado no meio de uma implementação, o caminho mais direto é simplesmente abrir, ou voltar, na sua pasta de /teach e contar em linguagem natural o que você acabou de esbarrar, em vez de tentar formalizar isso com um handoff.

Como escolher um tópico a partir do seu projeto

Já que "o meu projeto" não é um tópico válido para o /teach, o caminho é extrair os conceitos de dentro dele primeiro. Peça, numa conversa normal ali no repositório, ou com o /domain-modeling, uma lista do que está sendo usado, os padrões, as bibliotecas, as escolhas de arquitetura. Essa lista vira um menu, e cada item dela, isoladamente, já é um tópico válido, Clean Architecture, Kotlin Coroutines, CQRS, o que for.

Por tópico, não tudo de uma vez. Não vale a pena despejar a lista inteira numa pasta só esperando que o /teach organize sozinho, ele ensina um tópico de cada vez, e o MISSION.md existe para segurar um motivo coerente para aprender aquilo especificamente, algo que se dilui se forem dez assuntos misturados na mesma pasta. O jeito mais seguro é escolher um item da lista por vez e abrir uma pasta própria só para ele, uma para Clean Architecture, outra separada se um dia quiser Coroutines, por exemplo.

Cuidados práticos

Confira onde a primeira lição realmente foi salva antes de construir em cima dela, e nomeie a pasta explicitamente ao começar uma sessão nova, em vez de confiar que "o diretório atual" vai ser óbvio sozinho.

Vale lembrar, mesmo citando fontes, você não tem garantia absoluta de que nada ali foi inventado, só a palavra da própria skill.

Para se comunicar melhor no dia a dia

Ao contrário do /teach, essas rodam dentro da própria sessão de trabalho, para resolver um travamento pontual, uma decisão que não é sua, uma explicação que não aterrissou, ou documentação pensada para outro agente ler depois.

/to-questionnaire

Mesmo chat

Para quando uma decisão trava porque só uma outra pessoa consegue responder, não você. Em vez de te grillar sobre o assunto, ele te grilla sobre o envio, quem é essa pessoa, o que exatamente você precisa que ela responda, e gera um questionário em Markdown para entregar a ela, preenchido de forma assíncrona ou junto numa reunião.

Mais contexto

A diferença chave é essa inversão do que está sendo grillado. Um /grill-with-docs normal te pergunta sobre o assunto em si, porque assume que você tem a resposta. O /to-questionnaire assume o oposto, que você não tem, então as perguntas dele são sobre como formular o pedido, para quem mandar, e que formato de resposta você precisa de volta, não sobre o conteúdo da decisão.

Útil quando um grill trava numa pergunta que depende de alguém de fora, seu orientador, um cliente, alguém do time que sabe de uma regra de negócio que você não sabe. Em vez de travar o planejamento esperando essa resposta em algum lugar solto, você gera algo formal para levar até essa pessoa.

/wait-what

Mesmo chat

Dispare no exato momento em que uma resposta do agente não fizer sentido para você. Ele reformula a explicação em português claro, usando o vocabulário já registrado no seu CONTEXT.md, em vez de repetir a mesma explicação com as mesmas palavras.

Mais contexto

A diferença de só perguntar "não entendi, explica de novo" é que o /wait-what tenta identificar qual pedaço específico da explicação anterior não aterrissou, e reconstrói a partir dali, ancorado nos termos que o seu próprio projeto já usa, em vez de trazer um vocabulário genérico novo que também pode não fazer sentido.

Vale disparar na hora, ainda na mesma conversa onde a confusão aconteceu, porque ele depende do que acabou de ser dito para saber o que reformular.

/writing-for-agents

Qualquer sessão

Disciplina para escrever documentos pensados para serem lidos por agentes, não por pessoas, skills, arquivos AGENTS.md ou CLAUDE.md, e qualquer documento que um agente alcança seguindo um link ou caminho, em vez de ler direto na conversa.

Mais contexto

Escrever para um agente pede um estilo diferente de escrever para uma pessoa, mais explícito, menos ambíguo, com a informação mais importante logo no início, porque um agente não tem o mesmo faro que uma pessoa para inferir o que ficou implícito.

Vale a pena se você chegar a escrever uma skill sua com o /writing-great-skills, ou quiser deixar o CONTEXT.md e o AGENTS.md do seu projeto mais claros para as outras skills lerem, já que todas elas dependem desses arquivos para funcionar direito.

Front-end ou back-end: o que muda na prática

Nenhuma skill do pacote é exclusiva de front ou de back, todas trabalham em cima do que a entrevista já levantou. O que muda é qual comando vale puxar com mais força para cada lado — não é uma parada obrigatória da rota, é uma referência de ênfase.

Trabalho de tela

A dúvida costuma ser visual, então /prototype entra fácil depois do grill: ele já aciona sozinho a skill de frontend design do Claude Code, gerando variações comparáveis lado a lado antes de decidir. Vale testar de verdade no navegador antes de considerar pronto, não só ler o código gerado.

Trabalho de servidor, dado ou regra de negócio

Raramente passa por /prototype, a dúvida normalmente não é visual. Vale mais peso em /domain-modeling para desafiar os limites entre módulos, e em /codebase-design para desenhar a fronteira entre camadas antes do /implement.

E quando é dos dois lados ao mesmo tempo?

Qualquer sessão

Não existe um "modo full-stack" separado para ligar. O /to-tickets já corta cada ticket ponta a ponta por padrão, banco, API, tela, teste juntos na mesma fatia, em vez de separar um ticket de front do de back.

Mais contexto

Front e back só viram uma escolha consciente de verdade quando o trabalho é pequeno o bastante para nem passar por /to-tickets, indo direto de /grill-with-docs para /implement. Aí sim vale decidir, na hora, qual das duas ênfases da tabela acima usar dentro dessa sessão.

/domain-modeling

Qualquer sessão

É a disciplina que já roda por baixo do /grill-with-docs, mas também pode ser chamada sozinha, direto, sem abrir uma entrevista de feature nova. Serve para desafiar um termo ou uma decisão que já existe, comparando contra o CONTEXT.md e os s atuais do repositório.

Mais contexto

É a ferramenta certa para quando você quer questionar uma decisão por ter esquecido algo ou por dúvida, principalmente depois que ela já virou um ADR fechado. Em vez de editar o ADR antigo por cima, o formato correto é marcar o antigo como superado e escrever um novo, registrando o motivo da mudança, o campo de status de um ADR existe justamente para isso.

Como ele lê o CONTEXT.md e os ADRs direto do repositório, funciona em qualquer sessão, sem depender do histórico da conversa onde a decisão original foi tomada.

Ele também serve como um jeito indireto de gerar sugestão de melhoria para a ideia em si, já que estressar contra cenários expõe lacunas e casos de borda esquecidos. Se algo daí parecer interessante, é só levar como ponto de partida para uma sessão de /grill-with-docs.

/codebase-design

Qualquer sessão

Disciplina e vocabulário compartilhado para desenhar módulos profundos, interfaces pequenas, costuras limpas entre partes do sistema, testáveis pela própria interface.

Mais contexto
